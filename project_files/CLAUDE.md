# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Manifest is a structured, schema-driven checklist application built with React, Next.js, tRPC, Kysely, and PostgreSQL. The application enables users to create dynamic, reusable checklists with hierarchical page structures, questions with various answer types, and comprehensive response tracking.

## Architecture

### Workspace Structure

This is an npm workspaces monorepo with the main application in `apps/web/`. Root-level scripts delegate to the web workspace.

### Database Layer

**ORM:** Kysely with PostgreSQL
- Main database instance: `apps/web/src/api/database/kysely.ts`
- Type definitions: `apps/web/src/api/database/types.d.ts` (auto-generated by kysely-codegen)
- Schema used: Controlled by `DB_SCHEMA` environment variable (defaults to 'public')
- All queries log SQL and parameters to console

**Important: Client-Scoped Data**
- Most tables are multi-tenant and partitioned by `client_id`
- Use `applyClientScope()` from `apps/web/src/api/database/clientScoped.ts` to enforce client filtering on SELECT queries
- Client-scoped tables include: action, answer, checklist, claim, comment, doc, feeds, page, page_instance, question, question_response, and related tables
- User session contains `client_id` which must be used to scope queries

**Database schema regeneration:**
```bash
npx kysely-codegen --out-file apps/web/src/api/database/types.d.ts
# Regenerates types from database schema
```

### API Layer (tRPC)

**Structure:**
- Router setup: `apps/web/src/server/trpc/appRouter.ts`
- Individual routers: `apps/web/src/server/trpc/routers/*.ts`
- Context creation: `apps/web/src/server/trpc/context.ts` (provides session)
- Procedures: `apps/web/src/server/trpc/trpc.ts` (defines `publicProcedure` and `protectedProcedure`)

**Authentication:**
- Uses NextAuth with session-based auth
- `protectedProcedure` enforces authentication and provides typed `ProtectedContext`
- Context includes `session.user` with user details including `client_id`

**Query functions:**
- Complex database queries live in `apps/web/src/api/queries/*.ts`
- These are imported and used by tRPC routers
- Always accept `ProtectedContext` as first parameter for client scoping

**Validation:**
- Zod schemas in `apps/web/src/schemas/*.ts`
- Shared between frontend and backend for type safety

### Frontend

**State Management:**
- Zustand for global state
- State slices organized by domain: `apps/web/src/state/*/`
- Store types defined in `apps/web/src/state/storeTypes.ts`
- Main slices: AdminSlice, BreakdownSlice, ChecklistSlice, ChecklistsSlice, GlobalSlice, MetricsSlice

**tRPC Hooks:**
- Custom hooks wrap tRPC client: `apps/web/src/hooks/trpc/*.ts`
- Pattern: Export mutation/query wrappers with cache invalidation logic
- Example: `useAnswerTrpc()` exports `list`, `get`, `create`, `copy`, `update`, `remove`
- These hooks also export types derived from router inputs/outputs

**Component Organization:**
- Domain-based: `apps/web/src/components/{admin,auth,checklist,pages,metrics,etc}/`
- Common reusable components: `apps/web/src/components/common/`

**Routing:**
- Next.js App Router
- Protected routes: `apps/web/src/app/(protected)/`
- Public routes: `apps/web/src/app/(public)/`
- API routes: `apps/web/src/app/api/`

### Data Model Concepts

**Checklist hierarchy:**
- Checklists contain page instances
- Page instances reference page templates (page table)
- Pages contain questions
- Questions have answer options
- Page instances support nesting via `parent_instance_id`

**Templates vs. Instances:**
- Pages and questions are templates (reusable definitions)
- Page instances are specific occurrences in a checklist
- Supports versioning: `page.version` and `page_instance_status.template_version`

**Claims and Responses:**
- Checklists are assigned to claims via `checklist_claim` join table
- Users respond to questions, creating `question_response` records
- For questions with answer options, `question_response_answer` links responses to selected answers
- Freeform text goes in `question_response.response_text`

**Conditional page unlocking:**
- Answers can reference page instances via `answer.calls_instance_id`
- When a user selects such an answer, the referenced page instance is "unlocked"
- Recursive CTEs calculate unlocked page trees (see `getChecklistClaimProgress()`)

## Key Patterns

**Adding a new entity:**
1. Create/update database table (run SQL migration if needed)
2. Regenerate Kysely types: `npx kysely-codegen`
3. Create Zod schema in `apps/web/src/schemas/`
4. Create query functions in `apps/web/src/api/queries/`
5. Create tRPC router in `apps/web/src/server/trpc/routers/`
6. Register router in `apps/web/src/server/trpc/appRouter.ts`
7. Create frontend hook in `apps/web/src/hooks/trpc/`
8. Add Zustand state slice if needed

**Client scoping enforcement:**
- Always use `applyClientScope()` on SELECT queries for client-scoped tables
- Pass `ctx.session.user.client_id` from ProtectedContext
- This ensures users only see their organization's data

**Response handling:**
- Responses are saved in bulk on user action
- Use `question_response` for base response record
- Link answer selections via `question_response_answer`
- Audit logging: `response_audit_logs` tracks changes

## Working with Claude Code

### Token Optimization for Large Migrations

When performing large refactors or migrations (affecting 20+ files), optimize token usage while maintaining quality:

**1. Use Agents Aggressively**
- Delegate bulk file updates to the general-purpose agent
- Agents have separate token budgets that don't count against the main conversation
- Provide clear patterns and let the agent handle repetition

**2. Batch Operations Over Iteration**
- Write migration scripts (Node.js/bash) for repetitive changes instead of editing files one-by-one
- Use `find`, `sed`, `grep` in combination for bulk text replacements
- Only verify a few files manually, then apply to all

**3. Minimize Output Verbosity**
- Report only errors and final summary, not every successful operation
- Avoid listing all affected files unless specifically requested
- Skip intermediate verification messages when patterns are proven

**4. Strategic Tool Usage**
- Use `grep` with line limits instead of reading full files
- Make parallel tool calls when possible (multiple edits in one message)
- Trust the process after verifying pattern works 2-3 times

**5. Efficient File Operations**
- Read only what's needed (use `limit`/`offset` parameters)
- Batch related edits together
- Use `Bash` with regex for simple find-replace operations

**Goal:** Complete large migrations efficiently without compromising correctness or thoroughness. Verbose output is fine for complex logic, but repetitive operations should be streamlined.

### Migration Protocol

**Before Starting:**
- Review existing architecture and patterns
- Document current state in `project_files/MIGRATION_LOG.md`
- Identify all affected files (use agents for large searches)
- Test migration pattern on 2-3 files before bulk operations

**During Migration:**
- Use agents for bulk file updates (separate token budget)
- Verify TypeScript compilation after changes
- Check for edge cases (non-React contexts, event handlers, etc.)
- Fix errors immediately as they arise

**After Completion:**
- Run full type check and linting
- Document changes chronologically in MIGRATION_LOG.md
- Include: date, motivation, files changed, issues encountered, verification steps
- Update TESTING_PROGRESS.md if test files affected

### State Management (Zustand)

**Current Architecture (as of 2025-10-16):**
- Individual stores per domain (not centralized)
- All stores in `apps/web/src/stores/`
- Immer middleware for immutable updates
- Built-in reset functions per store
- MapSet enabled globally for Set/Map support

**Store Pattern:**
```typescript
import { create } from 'zustand';
import { immer } from 'zustand/middleware/immer';

interface MyState { /* ... */ }
interface MyActions { /* ... */ }
type MyStore = MyState & MyActions;

const initialState: MyState = { /* ... */ };

export const useMyStore = create<MyStore>()(
  immer((set, get) => ({
    ...initialState,
    myAction: (arg) => set((state) => { state.field = arg; }),
    reset: (partialState) => set((state) => {
      Object.assign(state, { ...initialState, ...partialState });
    }),
  }))
);
```

**Component Usage:**
```typescript
// Destructure state and actions
const field = useMyStore((state) => state.field);
const myAction = useMyStore((state) => state.myAction);

// Non-React context (event handlers, callbacks)
useMyStore.getState().myAction(value);
```
